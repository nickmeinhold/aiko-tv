Why Dart reaches the TV and Python doesn't

The instinct is to ask whether a Smart TV can run Python. That's the wrong question — and the right one tells you exactly what doing it anyway would cost.

The TV doesn't run Dart. It runs machine code (Tizen) or JavaScript (webOS). Dart's advantage isn't that it's a permitted language — it's that it has a downhill compile path to both, and someone already built the bridge.

01Tizen — Dart becomes a native binary

flutter-tizen does not ship a Dart interpreter to the TV. Dart is AOT-compiled to ARM machine code ahead of time, and what goes into the .tpk is a native Tizen app. The only runtime riding along is a small GC and snapshot loader linked into that binary.

Python has no equivalent move. CPython is an interpreter by construction: it needs libpython, the standard library present as importable files, and dynamic module loading at runtime. There is no dart compile aot analogue that turns a Python package into a self-contained ARM binary.

🧩 The first-order reason is the embedder no port exists

Tizen's supported app models are Web, .NET, and Native C/C++. Flutter isn't on that list either. flutter-tizen exists because Samsung wrote a native C++ Tizen app that hosts the Flutter engine — creating the Evas/EFL surface, pumping input, wiring the app lifecycle.

Nobody has written "CPython embedded in a native Tizen app." That's the actual asymmetry: not language permissions, but whose porting work already exists. Everything else is downstream of it.

Underneath the embedder sit the second-order problems, each its own project:

  • C extensions — numpy, pyzmq, Pillow, psutil are compiled .so files. Manylinux wheels won't load; each needs cross-compiling against Tizen's ARM sysroot and libc.
  • Confinement — Tizen apps are signed and run under SMACK, so what you can exec from a dropped-in binary is constrained.
  • Size — interpreter plus stdlib is tens of megabytes before any application code.

02webOS — the language question dissolves

Retail LG sets run packaged web apps. The platform executes JavaScript, full stop. Dart reaches that TV only by compiling to JS via dart2js — so it isn't "the TV runs Dart" in any sense; Dart is simply upstream in the toolchain from the thing the TV actually executes.

💥 The prior on-device finding proven, not inferred

downstream-webos was a Flutter Web app until 2026-06-20. Flutter Web crashes the LG C2's webview during engine bootstrap — before any app code executes. A 1.7 MB hello-world crashes identically to the full app, so it isn't bundle size; an isolated CanvasKit probe created a GPU surface and drew to it, and WASM validates true, so it isn't a WebGL/WASM limit. Plain HTML/JS, <video> and fetch all work perfectly.

The app is now vanilla HTML/JS with no build step — which is its whole virtue, and the thing any Dart route has to spend.

That leaves two routes, neither obviously right:

  • dart2js the aiko package into a JS bundle and <script> it in. The codec and dispatcher are pure Dart with no dart:io, so they compile fine — the crash was the Flutter engine, not Dart-compiled JS. Cost: a build step returns.
  • Use mqtt.js over WebSockets and hand-port the S-expression codec to JS, held to the same RFC-0001 vectors the Dart port is pinned to.

03The honest caveat: Python isn't impossible on webOS

Since WASM validates true on that C2, Pyodide — CPython compiled to WebAssembly — would genuinely load in that webview, and numpy ships in the Pyodide distribution.

I'd still not do it, and that's a judgement call rather than a capability limit. It's a 10 MB-plus download onto a TV SoC, and Pyodide can't open raw TCP sockets from the browser sandbox anyway — so Aiko's MQTT transport needs rewriting to WebSockets regardless. At which point you've done the hard part of the port and are running a Python-in-WASM stack to avoid writing one codec in JavaScript.

🛠️ The one thing to fix first actionable

aiko_services_dart/lib/src/transport/mqtt_transport.dart:4 imports package:mqtt_client/mqtt_server_client.dart, which pulls dart:io and makes the package non-web-compilable as written. Fine for Tizen; fatal for any webOS route. Split it with a conditional import at the transport seam now, while the seam is three files old.

The path of least resistance is Tizen plus the Dart port that already exists — AOT-to-native with a maintained embedder means there is almost nothing to build. Everything else, webOS and Python alike, is a porting project first and an Aiko integration second.
